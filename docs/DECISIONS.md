# Decisions

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| Use OTLP (`go.opentelemetry.io/proto/otlp`) as the wire format and span schema, rather than a hand-rolled schema | Custom protobuf/JSON span schema | OTLP is the de facto standard; every real instrumentation library (OTel SDKs, most vendor agents) already speaks it, so the collector works with real clients on day one instead of requiring a translation layer. Hand-rolling a schema means re-deriving decisions OTel already made (span kinds, status codes, resource attributes) with no benefit. | |
| Go for collector, writer, and loadgen, rather than Python | Python throughout, matching the analyzer | The collector and writer sit on the ingest hot path — high-throughput, concurrent, latency-sensitive. Go's concurrency model and static binaries (small containers, fast cold start, no interpreter/runtime overhead) fit that better than Python. Python is used for the analyzer instead, where the work is graph algorithms and statistics, not raw throughput. | |
| Redpanda (Kafka wire protocol) instead of Apache Kafka for local/dev | Kafka + Zookeeper (or KRaft) | Redpanda ships as a single binary/container with no separate coordination service, starts fast, and is Kafka-API-compatible so `franz-go` and any future Kafka-speaking client works unmodified. Lower local resource footprint and fewer moving parts for a docker-compose dev environment. Whether this choice holds for a production deployment is a later decision, not made here. | |
| ClickHouse `spans` table: `ORDER BY (trace_id, span_id)`, `PARTITION BY toDate(start_time)`, with a `service_name` set skip index | `ORDER BY (service_name, start_time)` | The table must serve two opposed access patterns: point lookup by `trace_id` (interactive, latency-sensitive) and p99 duration aggregation by `service_name` over a time range (tolerant of scanning). Leading the sort key with `trace_id` makes the interactive lookup fast via primary-key pruning; the aggregation query instead relies on partition pruning by date plus a set skip index on `service_name`, degrading to a columnar scan of two narrow columns rather than a full-table scan. Reasoning documented in full as a comment above the table in `deploy/clickhouse/init.sql`. If per-service aggregation becomes the dominant query pattern, the fix is an additional materialized view/projection ordered by `(service_name, start_time)`, not reordering this table's primary key. | |
| Three independent Go modules (`collector/go.mod`, `writer/go.mod`, `loadgen/go.mod`) tied together with a root `go.work` for local development | Single shared Go module for all three services | Each service ships as its own container with its own dependency footprint (e.g. `loadgen` doesn't need `clickhouse-go` or `franz-go`; `writer` doesn't need the gRPC server bits `collector` needs). Independent `go.mod` files keep each image's dependency graph minimal and let the services version independently later. `go.work` keeps cross-module local development (e.g. `go build ./...` from the repo root, IDE tooling) convenient without merging the modules. | |
| `collector` and `writer` container images: Alpine base instead of distroless | `gcr.io/distroless/static-debian12` | Both services need a docker-compose `healthcheck` that curls their own `/healthz` endpoint. Distroless images ship no shell and no HTTP client, so an in-container healthcheck isn't possible without adding a second binary. Alpine's bundled BusyBox `wget` covers this with negligible image-size cost over distroless, without pulling in a full OS. | |
| `collector` and `writer` expose `/healthz` and `/metrics` on a dedicated HTTP port, separate from `collector`'s gRPC port | Serve health/metrics on the same port/protocol as the main service traffic | OTLP traffic is gRPC; health checks and Prometheus scraping are plain HTTP. Splitting the ports avoids protocol-muxing complexity and matches the pattern most OTel-ecosystem components already use (e.g. OTel Collector's own `:13133` health and `:8888` metrics ports). | |
| `writer` stays running (serving `/healthz` and `/metrics`) after its Phase 0 startup connectivity checks pass, rather than checking connectivity and exiting | Exit 0 immediately after a successful connectivity check | docker-compose `healthcheck` and `depends_on: condition: service_healthy` require a long-running process to poll. An exit-on-success process would report as "exited (0)", which compose does not treat as healthy, breaking the deliberate dependency ordering (`prometheus` waiting on `writer`, etc.). | |
| `duration_ns` and `start_time` (DateTime64) as `MATERIALIZED` columns in the `spans` table, derived from the raw `start_time_unix_nano`/`end_time_unix_nano` fields | Store `duration_ns` as a value written directly by the writer | Deriving `duration_ns` from the two nanosecond timestamps guarantees it can never drift out of sync with them — there's only one source of truth. `start_time` as a materialized `DateTime64(9)` exists solely so `PARTITION BY`/TTL have a native date/time expression to operate on; the raw nanosecond epoch fields remain the fields the writer actually inserts. | |

Evidence is left blank throughout — nothing in Phase 0 has been load-tested
or benchmarked yet. `docs/BENCHMARKS.md` gets filled in as later phases
produce real measurements; no numbers are invented here.
