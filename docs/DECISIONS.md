# Decisions

## Phase 0

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| Use OTLP (`go.opentelemetry.io/proto/otlp`) as the wire format and span schema, rather than a hand-rolled schema | Custom protobuf/JSON span schema | OTLP is the de facto standard; every real instrumentation library (OTel SDKs, most vendor agents) already speaks it, so the collector works with real clients on day one instead of requiring a translation layer. Hand-rolling a schema means re-deriving decisions OTel already made (span kinds, status codes, resource attributes) with no benefit. | |
| Go for collector, writer, and loadgen, rather than Python | Python throughout, matching the analyzer | The collector and writer sit on the ingest hot path — high-throughput, concurrent, latency-sensitive. Go's concurrency model and static binaries (small containers, fast cold start, no interpreter/runtime overhead) fit that better than Python. Python is used for the analyzer instead, where the work is graph algorithms and statistics, not raw throughput. | |
| Redpanda (Kafka wire protocol) instead of Apache Kafka for local/dev | Kafka + Zookeeper (or KRaft) | Redpanda ships as a single binary/container with no separate coordination service, starts fast, and is Kafka-API-compatible so `franz-go` and any future Kafka-speaking client works unmodified. Lower local resource footprint and fewer moving parts for a docker-compose dev environment. Whether this choice holds for a production deployment is a later decision, not made here. | |
| ClickHouse `spans` table: `ORDER BY (trace_id, span_id)`, `PARTITION BY toDate(start_time)`, with a `service_name` set skip index | `ORDER BY (service_name, start_time)` | The table must serve two opposed access patterns: point lookup by `trace_id` (interactive, latency-sensitive) and p99 duration aggregation by `service_name` over a time range (tolerant of scanning). Leading the sort key with `trace_id` makes the interactive lookup fast via primary-key pruning; the aggregation query instead relies on partition pruning by date plus a set skip index on `service_name`, degrading to a columnar scan of two narrow columns rather than a full-table scan. Reasoning documented in full as a comment above the table in `deploy/clickhouse/init.sql`. If per-service aggregation becomes the dominant query pattern, the fix is an additional materialized view/projection ordered by `(service_name, start_time)`, not reordering this table's primary key. | |
| Three independent Go modules (`collector/go.mod`, `writer/go.mod`, `loadgen/go.mod`) tied together with a root `go.work` for local development | Single shared Go module for all three services | Each service ships as its own container with its own dependency footprint (e.g. `loadgen` doesn't need `clickhouse-go` or `franz-go`; `writer` doesn't need the gRPC server bits `collector` needs). Independent `go.mod` files keep each image's dependency graph minimal and let the services version independently later. `go.work` keeps cross-module local development (e.g. `go build ./...` from the repo root, IDE tooling) convenient without merging the modules. | |
| `collector` and `writer` container images: Alpine base instead of distroless | `gcr.io/distroless/static-debian12` | Both services need a docker-compose `healthcheck` that curls their own `/healthz` endpoint. Distroless images ship no shell and no HTTP client, so an in-container healthcheck isn't possible without adding a second binary. Alpine's bundled BusyBox `wget` covers this with negligible image-size cost over distroless, without pulling in a full OS. | |
| `collector` and `writer` expose `/healthz` and `/metrics` on a dedicated HTTP port, separate from `collector`'s gRPC port | Serve health/metrics on the same port/protocol as the main service traffic | OTLP traffic is gRPC; health checks and Prometheus scraping are plain HTTP. Splitting the ports avoids protocol-muxing complexity and matches the pattern most OTel-ecosystem components already use (e.g. OTel Collector's own `:13133` health and `:8888` metrics ports). | |
| `writer` stays running (serving `/healthz` and `/metrics`) after its Phase 0 startup connectivity checks pass, rather than checking connectivity and exiting | Exit 0 immediately after a successful connectivity check | docker-compose `healthcheck` and `depends_on: condition: service_healthy` require a long-running process to poll. An exit-on-success process would report as "exited (0)", which compose does not treat as healthy, breaking the deliberate dependency ordering (`prometheus` waiting on `writer`, etc.). | |
| `duration_ns` and `start_time` (DateTime64) as `MATERIALIZED` columns in the `spans` table, derived from the raw `start_time_unix_nano`/`end_time_unix_nano` fields | Store `duration_ns` as a value written directly by the writer | Deriving `duration_ns` from the two nanosecond timestamps guarantees it can never drift out of sync with them — there's only one source of truth. `start_time` as a materialized `DateTime64(9)` exists solely so `PARTITION BY`/TTL have a native date/time expression to operate on; the raw nanosecond epoch fields remain the fields the writer actually inserts. | |

Evidence is left blank throughout Phase 0 — nothing had been load-tested or
benchmarked yet at that point.

## Phase 1

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| Delivery semantics: at-least-once, deduplicated by ClickHouse `ReplacingMergeTree(ingested_at)` rather than by the writer | Exactly-once (transactional Kafka consume + ClickHouse insert), or dedup logic in the writer itself | Exactly-once across a consume-then-insert-into-a-different-system boundary requires distributed transactions or idempotency keys ClickHouse doesn't natively support well at this table's write volume. Pushing dedup to `ReplacingMergeTree` keeps the writer simple (insert, retry, commit — no dedup bookkeeping) and matches spans' natural idempotency: the same (trace_id, span_id) redelivered has identical content, so which copy "wins" a merge doesn't matter. Trade-off: readers must use `FINAL` (or accept eventual, merge-driven dedup) to see exact counts — not free, but confined to query time. | |
| Kafka partition key: raw `trace_id` bytes | Round-robin / no key (max throughput, no ordering guarantee); `span_id` (finer-grained, but scatters a trace's spans across partitions) | Every span of a trace must land on the same partition so a per-partition consumer sees them in a consistent relative order — load-bearing for Phase 2's topology reconstruction, which needs a trace's spans processed together. Kafka's default partitioner hashes the record key, so same key -> same partition is automatic; no custom partitioner needed. Verified with a unit test (`kafkaproducer.TestBuildRecordSameTraceIDSameKey`) that two spans sharing a trace_id always produce the same record key. | |
| Backpressure: an explicit bounded, blocking queue (`internal/boundedqueue`) between a dedicated fetch/decode goroutine and the batch/flush loop, rather than a single goroutine relying on franz-go's own fetch loop for backpressure | A single-goroutine loop — poll, decode, append to batch, flush on trigger, repeat — with no explicit queue and no second goroutine | Stated plainly: the simpler single-goroutine design would also have worked. franz-go's `PollFetches` naturally stalls fetching more records while the caller is busy (retrying a failed insert, in our case), so "stall, never buffer unboundedly" falls out of that loop for free, the same way it does here. The reason to add the queue and the second goroutine anyway was testability: it turns "the writer doesn't buffer unboundedly" from a claim about how we *use* a third-party client into a property of a small piece of code we own and can unit test in isolation (`boundedqueue.TestPushBlocksWhenFullAndUnblocksOnPop`) without spinning up Kafka. That benefit has a real cost, not just extra files: `flush` is now reachable from two goroutines (the batch loop and franz-go's `OnPartitionsRevoked` callback, which franz-go can invoke on its own goroutine at any time), so it's guarded by a mutex (`consumer.flushMu`) that wouldn't need to exist under the simpler design. That's a real piece of concurrent-correctness surface accepted purely so the backpressure property could be independently unit-tested — not because the extra machinery was required to make backpressure work. | Manual failure test: with ClickHouse stopped, writer memory stayed flat at 11.95MiB/7.749GiB (0.15%) over a sustained outage while consumer lag rose to ~2510 spans across 4 partitions — confirms growth went to Kafka lag, not process memory. |
| Batch flush: 5000 rows or 2 seconds, whichever fires first (both configurable via `WRITER_BATCH_MAX_SIZE` / `WRITER_FLUSH_INTERVAL`) | Fixed-size only (simpler, but stalls low-throughput partitions indefinitely); fixed-time only (simpler, but caps throughput at low-latency load) | Size-only starves the "trickle" case — a handful of spans/sec would sit unflushed forever below any reasonable size threshold. Time-only wastes batching efficiency under bursts big enough to hit a size bound well before the timer would. The OR-whichever-first policy is standard for this exact reason. | At the throughput levels exercised so far (up to ~150 spans/sec via loadgen), only the time bound has actually fired — `writer_batch_size` histogram shows all observed batches under 500 rows, well below the 5000 size trigger. The size-triggered flush path is unit-tested (`batcher.TestAddTriggersFlushAtMaxSize`) but not yet exercised by a real end-to-end run — see `docs/BENCHMARKS.md`'s "Known gap" note for the throughput math on why. |
| Kafka topic `spans`: 4 partitions, created explicitly by a one-shot `redpanda-topic-init` compose service before collector/writer start | Let the broker auto-create the topic on first produce (default partition count, usually 1) | Partition count is effectively fixed at creation time — changing it later reshuffles which keys land on which partition, breaking the "same trace_id always same partition" guarantee for any trace whose spans straddle the change. Deciding it explicitly, once, up front avoids that trap. 4 is enough to make partition-level behavior (skew, per-partition lag, rebalances) observable in Phase 6 without complicating local runs with a large partition count. | |
| Collector denormalizes `service.name` from the parent `Resource` onto each individual `Span`'s own attributes before publishing, rather than publishing OTLP's native `ResourceSpans` structure (Resource + spans) to Kafka | Publish a single-span `ResourceSpans` wrapper (one Resource, one ScopeSpans, one Span) per Kafka message, preserving full OTLP structure | I wanted one Kafka message per span, serialized as a literal OTLP `tracepb.Span` — not a wrapper message. But `service_name` (a dedicated, indexed column in the schema) lives on `Resource`, not `Span`. Copying it onto the span's own attributes before serializing keeps messages to a single flat `tracepb.Span`, staying protobuf end-to-end with no custom envelope, at the cost of ~20-30 bytes of duplicated attribute data per span. The writer strips it back out of the `Attributes` map column on the way in, since it already has its own column. | |
| Collector's `Export` RPC returns after admission to a bounded in-flight producer queue, not after the Kafka broker ack | Block `Export` until the broker acks every span in the request (synchronous, strongly consistent from the caller's point of view) | I wanted an async producer with a bounded in-flight limit, where a full buffer surfaces as a synchronous error back to the caller — that only makes sense if normal admission doesn't wait for the broker round trip either. The cost: `Export` can return success for a span that later fails to publish after retries are exhausted (broker down, etc.) — that span is silently lost from the caller's perspective, though not from ours: it's counted (`collector_publish_errors_total{reason="produce_failed"}`) and logged. I wanted that specific failure mode — a dropped span — to always be counted and logged rather than treated as a default best-effort outcome nobody has to think about. | |
| Integration tests (`/integration` module) drive the real `docker-compose.yml` stack via `docker compose` CLI calls (`os/exec`), rather than testcontainers-go | testcontainers-go, which manages containers programmatically from within the test process | I already had a working, hand-tuned `docker-compose.yml` with correct healthcheck-based dependency ordering; testcontainers-go would mean re-expressing that same topology a second way in Go code, or awkwardly wrapping `docker-compose.yml` through testcontainers' own compose support. Shelling out to the `docker compose` CLI directly reuses the compose file as the single source of truth and adds zero new dependencies to the module (stdlib only). Trade-off: requires a `docker` CLI with the compose plugin on `PATH` wherever these tests run — true in CI, and true for local dev, but not inside a bare `golang` container without also installing Docker's CLI into it. I confirmed this by cross-compiling the test binary in a `golang` container and running the resulting binary directly against the host's native Docker instead. | |
| Integration tests are gated behind a `-tags=integration` build constraint and are **not** part of the default `go vet`/`build`/`test`/`golangci-lint` CI matrix | Add `integration` as a fourth entry in the existing CI job's module matrix | They spin up the full docker-compose stack (build images, start 6 containers, run for ~1 minute) and stop/start a real container mid-test — appropriate for an on-demand or nightly job, not for every push/PR the way the fast unit-test matrix is. Excluding them from the default matrix keeps "CI green" meaning "the fast checks pass," not "a minute-plus Docker orchestration run passed." Wiring an actual CI job for them (with Docker available in the runner) is left for whenever that cost is worth paying, not built speculatively here. | |

Evidence is filled in above only where this phase actually measured
something (the two failure-mode Evidence cells); everywhere else is left
blank rather than guessed at. `docs/BENCHMARKS.md` still has no filled-in
Phase 1 numbers — the measurements taken here were correctness/behavioral
checks (memory bounded, lag rises and recovers, batch sizes observed), not
throughput/latency benchmarks, so they're recorded here rather than there.

## Phase 2 (partial: loadgen ground truth/fault injection + trace reassembly only)

Clock skew detection, service topology aggregation, and the accuracy-eval
harness are separate pieces of work I haven't built yet, so I'm not
recording decisions about them here as if they'd already been made — that
would be guessing ahead of doing the work.

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| Analyzer processes ClickHouse in epoch-aligned, fixed-size windows on a poll loop, not a streaming consumer | A real streaming pipeline (Kafka consumer group reading spans directly, à la the writer) | Windowed batch is simpler to reason about and test: a window's correctness doesn't depend on consumer group rebalances, partition assignment, or in-order delivery — it's "query a time range, process what's there." The cost is latency (a trace isn't reassembled until its window closes) and repeated ClickHouse scans instead of a continuous stream — both acceptable for what this phase needs to prove out first: whether reassembly is *correct*, not how fast it can go. | |
| Watermark delay of 30s (window size 60s) before a window is considered closed | A shorter watermark (less end-to-end lag) or a longer one (fewer late spans) | I don't have a measured spans-arrive-how-late-in-practice distribution yet, so I picked half the window size as a starting point that's easy to reason about, not a tuned value. This is the kind of number that should move once the fault sweep (unbuilt) shows how it trades off against late_spans_total. | |
| Windows are epoch-aligned (`floor(unix_seconds / window_seconds)`), anchored to the Unix epoch, not to analyzer startup time or a calendar day | Align windows to midnight, or to whenever the analyzer process starts | Epoch alignment means two analyzer instances (or a restarted one) agree on window boundaries without coordinating, and — the reason it's in this table — it's *why* the midnight-partition-straddle requirement turned out to be about the ClickHouse query, not the windowing logic: since 86400 is divisible by the default 60s window, midnight always lands exactly on a window boundary, so a window can never actually straddle it. What can straddle it is the SQL query if it's written as `toDate(start_time) = X` instead of a start_time range — see reader.py and its dedicated test in tests_integration/. | |
| Orphans (span whose parent_span_id doesn't resolve in the window) are recorded and classified, never dropped or reattached to a guessed parent | Silently drop spans with no resolvable parent; or attach them to the trace's root as a fallback | Both alternatives destroy information a later accuracy measurement needs: dropping loses the span entirely from any output, and reattaching to the root fabricates a parent/child relationship that was never real, which would corrupt exactly the "span attachment accuracy" metric this phase exists to eventually produce. Keeping every span, honestly labeled, is the only choice that doesn't quietly bias a future measurement. | |
| An orphan's own descendants are classified "ok" (reachable from the orphan), not swept into "cycle_rejected" just because they're unreachable from the trace's true root | Classify anything not reachable from a true root as one bucket (e.g. just "incomplete") | These are different failure signatures with different causes: a genuine cycle is malformed/impossible data, while a subtree hanging off an orphan is perfectly well-formed data that's simply missing *its own* ancestor. Conflating them would make "cycle_rejected" fire constantly in the completely ordinary case of a dropped mid-trace span with children — which is exactly what --drop-rate produces — making that classification useless for actually finding real cycles. The fix was seeding reachability from every orphan as well as every true root, and only labeling something cycle_rejected if it's unreachable from *both* sets. See reassembly.py's module docstring and `test_orphan_descendants_are_ok_not_cycle_rejected`. | |
| Ground truth is written by loadgen directly to ClickHouse (`ground_truth_spans`/`ground_truth_edges`), bypassing the collector/writer pipeline entirely | Send ground truth through the same collector -> Kafka -> writer path as real spans, tagged somehow to distinguish it | Ground truth has to record what was *generated*, before any fault runs — "faults must be applied after ground truth is recorded" is the one rule this whole phase hangs off. Routing it through the pipeline under test would make ground truth subject to the same drops/delays/reordering it's supposed to be the answer key for, which is circular. A direct write is also just simpler: loadgen already needs a ClickHouse connection for nothing else, so it's a small, explicit dependency rather than smuggling test-only semantics into the production ingest path. | |
| loadgen now requires ClickHouse connectivity at startup (fails fast if unreachable), same as writer | Make ground truth recording optional/best-effort, so loadgen still runs standalone against just a collector | Ground truth isn't a nice-to-have instrumentation add-on in this phase, it's the central mechanism the phase exists to build — a loadgen run with silently-skipped ground truth would produce traces with no way to ever check their accuracy. Fail-fast here matches the same reasoning collector and writer already use for their own required dependencies. | |
| Fault injectors operate on `[]spanplan.PlannedSpan` (span + service + Delay + Drop), and the emitter groups by actual Delay value before sending, rather than injectors mutating `[]*tracepb.Span` in place as the Phase 0 stub signature implied | Keep faults as pure span-content transforms (e.g. a "drop" fault just returns a shorter slice, as the original doc comment described) | Two of the fault types I wanted — out-of-order and late-arrival — are specifically about *when* a span is emitted, not what it contains. A `[]Span -> []Span` transform has nowhere to express "send this 90 seconds from now." Once delay had to be representable, drop became "a delay of never" naturally, so both live on the same PlannedSpan.Delay/.Drop pair rather than as different mechanisms. This meant changing loadgen's emit path from one Export call per trace to one call per (trace, delay-bucket) — more RPCs when a fault is active, none extra when it isn't (an all-zero-delay plan still sends as a single call). | |
| Clock-skew fault injection (`--clock-skew`) is not implemented yet, even though it's one of the four fault types this phase's brief-in-my-own-head originally scoped together with the other three | Implement injection now, since it's "just" mutating a span's timestamps, and add detection later | Shipping the injector without anything that can detect or account for it would mean a `--clock-skew` flag sits in loadgen doing damage with no way to verify it's doing the *right* damage — I'd have no way to distinguish "skew detection works" from "skew detection was never built." Landing injection and detection together, when I get to it, means the very first time skew injection exists at all, there's already a measured detected-vs-true-offset number to check it against. | |
| Analyzer reads ClickHouse over HTTP (`clickhouse-connect`, port 8123), not the native protocol the writer uses (`clickhouse-go`, port 9000) | Use a native-protocol Python client to match the writer's transport | No mature native-protocol client for Python matches clickhouse-connect's maturity/adoption; HTTP is simpler to reason about from Python (plain requests-style semantics, no wire protocol to get wrong) and perfectly adequate for windowed batch queries, which aren't latency-sensitive the way the writer's per-span inserts are. | |
| Analyzer's window and late-arrival queries use `SELECT ... FINAL` | Query without FINAL and accept that an unmerged ReplacingMergeTree duplicate (writer at-least-once redelivery) might appear as two rows | Reassembly logic assumes one row per real span; a still-unmerged duplicate would silently inflate span_count and could even fabricate a fake "multiple roots" or double-counted orphan. FINAL costs query-time merge work but guarantees the row count reassembly sees matches reality regardless of background merge timing. Revisit if this becomes a real bottleneck — nothing here has measured whether it is one. | |
| Late-span detection uses a single rolling cursor (`last_late_check` timestamp + the oldest still-open window's start as a boundary), not per-window precise bookkeeping | Track, per processed window, exactly when it was finalized, and check each window's own late-arrivals against its own finalization time | A single cursor is simpler and only trades precision at the margins: it can occasionally classify something as "late" a poll cycle earlier or later than the most precise per-window accounting would, but the count and the fact that it's not silently dropped — the actual requirement — hold either way. Reached for the more complex design only if the simple one turns out to be wrong, not preemptively. | |
