# Decisions

## Phase 0

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| Use OTLP (`go.opentelemetry.io/proto/otlp`) as the wire format and span schema, rather than a hand-rolled schema | Custom protobuf/JSON span schema | OTLP is the de facto standard; every real instrumentation library (OTel SDKs, most vendor agents) already speaks it, so the collector works with real clients on day one instead of requiring a translation layer. Hand-rolling a schema means re-deriving decisions OTel already made (span kinds, status codes, resource attributes) with no benefit. | |
| Go for collector, writer, and loadgen, rather than Python | Python throughout, matching the analyzer | The collector and writer sit on the ingest hot path — high-throughput, concurrent, latency-sensitive. Go's concurrency model and static binaries (small containers, fast cold start, no interpreter/runtime overhead) fit that better than Python. Python is used for the analyzer instead, where the work is graph algorithms and statistics, not raw throughput. | |
| Redpanda (Kafka wire protocol) instead of Apache Kafka for local/dev | Kafka + Zookeeper (or KRaft) | Redpanda ships as a single binary/container with no separate coordination service, starts fast, and is Kafka-API-compatible so `franz-go` and any future Kafka-speaking client works unmodified. Lower local resource footprint and fewer moving parts for a docker-compose dev environment. Whether this choice holds for a production deployment is a later decision, not made here. | |
| ClickHouse `spans` table: `ORDER BY (trace_id, span_id)`, `PARTITION BY toDate(start_time)`, with a `service_name` set skip index | `ORDER BY (service_name, start_time)` | The table must serve two opposed access patterns: point lookup by `trace_id` (interactive, latency-sensitive) and p99 duration aggregation by `service_name` over a time range (tolerant of scanning). Leading the sort key with `trace_id` makes the interactive lookup fast via primary-key pruning; the aggregation query instead relies on partition pruning by date plus a set skip index on `service_name`, degrading to a columnar scan of two narrow columns rather than a full-table scan. Reasoning documented in full as a comment above the table in `deploy/clickhouse/init.sql`. If per-service aggregation becomes the dominant query pattern, the fix is an additional materialized view/projection ordered by `(service_name, start_time)`, not reordering this table's primary key. | |
| Three independent Go modules (`collector/go.mod`, `writer/go.mod`, `loadgen/go.mod`) tied together with a root `go.work` for local development | Single shared Go module for all three services | Each service ships as its own container with its own dependency footprint (e.g. `loadgen` doesn't need `clickhouse-go` or `franz-go`; `writer` doesn't need the gRPC server bits `collector` needs). Independent `go.mod` files keep each image's dependency graph minimal and let the services version independently later. `go.work` keeps cross-module local development (e.g. `go build ./...` from the repo root, IDE tooling) convenient without merging the modules. | |
| `collector` and `writer` container images: Alpine base instead of distroless | `gcr.io/distroless/static-debian12` | Both services need a docker-compose `healthcheck` that curls their own `/healthz` endpoint. Distroless images ship no shell and no HTTP client, so an in-container healthcheck isn't possible without adding a second binary. Alpine's bundled BusyBox `wget` covers this with negligible image-size cost over distroless, without pulling in a full OS. | |
| `collector` and `writer` expose `/healthz` and `/metrics` on a dedicated HTTP port, separate from `collector`'s gRPC port | Serve health/metrics on the same port/protocol as the main service traffic | OTLP traffic is gRPC; health checks and Prometheus scraping are plain HTTP. Splitting the ports avoids protocol-muxing complexity and matches the pattern most OTel-ecosystem components already use (e.g. OTel Collector's own `:13133` health and `:8888` metrics ports). | |
| `writer` stays running (serving `/healthz` and `/metrics`) after its Phase 0 startup connectivity checks pass, rather than checking connectivity and exiting | Exit 0 immediately after a successful connectivity check | docker-compose `healthcheck` and `depends_on: condition: service_healthy` require a long-running process to poll. An exit-on-success process would report as "exited (0)", which compose does not treat as healthy, breaking the deliberate dependency ordering (`prometheus` waiting on `writer`, etc.). | |
| `duration_ns` and `start_time` (DateTime64) as `MATERIALIZED` columns in the `spans` table, derived from the raw `start_time_unix_nano`/`end_time_unix_nano` fields | Store `duration_ns` as a value written directly by the writer | Deriving `duration_ns` from the two nanosecond timestamps guarantees it can never drift out of sync with them — there's only one source of truth. `start_time` as a materialized `DateTime64(9)` exists solely so `PARTITION BY`/TTL have a native date/time expression to operate on; the raw nanosecond epoch fields remain the fields the writer actually inserts. | |

Evidence is left blank throughout Phase 0 — nothing had been load-tested or
benchmarked yet at that point.

## Phase 1

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| Delivery semantics: at-least-once, deduplicated by ClickHouse `ReplacingMergeTree(ingested_at)` rather than by the writer | Exactly-once (transactional Kafka consume + ClickHouse insert), or dedup logic in the writer itself | Exactly-once across a consume-then-insert-into-a-different-system boundary requires distributed transactions or idempotency keys ClickHouse doesn't natively support well at this table's write volume. Pushing dedup to `ReplacingMergeTree` keeps the writer simple (insert, retry, commit — no dedup bookkeeping) and matches spans' natural idempotency: the same (trace_id, span_id) redelivered has identical content, so which copy "wins" a merge doesn't matter. Trade-off: readers must use `FINAL` (or accept eventual, merge-driven dedup) to see exact counts — not free, but confined to query time. | |
| Kafka partition key: raw `trace_id` bytes | Round-robin / no key (max throughput, no ordering guarantee); `span_id` (finer-grained, but scatters a trace's spans across partitions) | Every span of a trace must land on the same partition so a per-partition consumer sees them in a consistent relative order — load-bearing for Phase 2's topology reconstruction, which needs a trace's spans processed together. Kafka's default partitioner hashes the record key, so same key -> same partition is automatic; no custom partitioner needed. Verified with a unit test (`kafkaproducer.TestBuildRecordSameTraceIDSameKey`) that two spans sharing a trace_id always produce the same record key. | |
| Backpressure: an explicit bounded, blocking queue (`internal/boundedqueue`) between the writer's Kafka-fetch/decode step and its batch/flush step, rather than relying only on the Kafka client's internal buffering | Rely solely on franz-go's own fetch buffering; single-goroutine fetch-decode-batch-flush loop with no explicit queue | franz-go's `MaxBufferedRecords` option turned out to be producer-only (confirmed via `go doc`) — there's no equivalent consumer-side "cap total buffered fetched records" knob to lean on. Owning the bounded buffer directly makes "stall, never buffer unboundedly" a property of code we wrote and could unit test in isolation (`boundedqueue.TestPushBlocksWhenFullAndUnblocksOnPop`), not an assumption about a third-party client's internals. | Manual failure test: with ClickHouse stopped, writer memory stayed flat at 11.95MiB/7.749GiB (0.15%) over a sustained outage while consumer lag rose to ~2510 spans across 4 partitions — confirms growth went to Kafka lag, not process memory. |
| Batch flush: 5000 rows or 2 seconds, whichever fires first (both configurable via `WRITER_BATCH_MAX_SIZE` / `WRITER_FLUSH_INTERVAL`) | Fixed-size only (simpler, but stalls low-throughput partitions indefinitely); fixed-time only (simpler, but caps throughput at low-latency load) | Size-only starves the "trickle" case — a handful of spans/sec would sit unflushed forever below any reasonable size threshold. Time-only wastes batching efficiency under bursts big enough to hit a size bound well before the timer would. The OR-whichever-first policy is standard for this exact reason. | At the throughput levels exercised so far (up to ~150 spans/sec via loadgen), only the time bound has actually fired — `writer_batch_size` histogram shows all observed batches under 500 rows, well below the 5000 size trigger. The size-triggered flush path is unit-tested (`batcher.TestAddTriggersFlushAtMaxSize`) but not yet exercised by a real end-to-end run — see the phase report for how this was verified. |
| Kafka topic `spans`: 4 partitions, created explicitly by a one-shot `redpanda-topic-init` compose service before collector/writer start | Let the broker auto-create the topic on first produce (default partition count, usually 1) | Partition count is effectively fixed at creation time — changing it later reshuffles which keys land on which partition, breaking the "same trace_id always same partition" guarantee for any trace whose spans straddle the change. Deciding it explicitly, once, up front avoids that trap. 4 is enough to make partition-level behavior (skew, per-partition lag, rebalances) observable in Phase 6 without complicating local runs with a large partition count. | |
| Collector denormalizes `service.name` from the parent `Resource` onto each individual `Span`'s own attributes before publishing, rather than publishing OTLP's native `ResourceSpans` structure (Resource + spans) to Kafka | Publish a single-span `ResourceSpans` wrapper (one Resource, one ScopeSpans, one Span) per Kafka message, preserving full OTLP structure | The phase brief calls for "one Kafka message per span... the span serialized as OTLP protobuf" — a literal `tracepb.Span`, not a wrapper message. But `service_name` (a dedicated, indexed column in the schema) lives on `Resource`, not `Span`. Copying it onto the span's own attributes before serializing keeps messages to a single flat `tracepb.Span` (matching the brief, staying protobuf end-to-end, no custom envelope) at the cost of ~20-30 bytes of duplicated attribute data per span. The writer strips it back out of the `Attributes` map column on the way in, since it already has its own column. | |
| Collector's `Export` RPC returns after admission to a bounded in-flight producer queue, not after the Kafka broker ack | Block `Export` until the broker acks every span in the request (synchronous, strongly consistent from the caller's point of view) | The brief specifies an async producer with a bounded in-flight limit and says a full buffer should be a synchronous error back to the caller — which only makes sense if normal admission doesn't wait for the broker round trip either. The cost: `Export` can return success for a span that later fails to publish after retries are exhausted (broker down, etc.) — that span is silently lost from the caller's perspective, though not from ours: it's counted (`collector_publish_errors_total{reason="produce_failed"}`) and logged. This is the specific case the brief flags: "if you drop, it must be counted and logged" rather than treated as a default best-effort outcome nobody has to think about. | |
| Integration tests (`/integration` module) drive the real `docker-compose.yml` stack via `docker compose` CLI calls (`os/exec`), rather than testcontainers-go | testcontainers-go, which manages containers programmatically from within the test process | The project already has a working, hand-tuned `docker-compose.yml` with correct healthcheck-based dependency ordering; testcontainers-go would mean re-expressing that same topology a second way in Go code, or awkwardly wrapping `docker-compose.yml` through testcontainers' own compose support. Shelling out to the `docker compose` CLI directly reuses the compose file as the single source of truth and adds zero new dependencies to the module (stdlib only). Trade-off: requires a `docker` CLI with the compose plugin on `PATH` wherever these tests run — true in CI, and true for local dev, but not inside a bare `golang` container without also installing Docker's CLI into it (see the phase report for how this was verified). | |
| Integration tests are gated behind a `-tags=integration` build constraint and are **not** part of the default `go vet`/`build`/`test`/`golangci-lint` CI matrix | Add `integration` as a fourth entry in the existing CI job's module matrix | They spin up the full docker-compose stack (build images, start 6 containers, run for ~1 minute) and stop/start a real container mid-test — appropriate for an on-demand or nightly job, not for every push/PR the way the fast unit-test matrix is. Excluding them from the default matrix keeps "CI green" meaning "the fast checks pass," not "a minute-plus Docker orchestration run passed." Wiring an actual CI job for them (with Docker available in the runner) is left for whenever that cost is worth paying, not built speculatively here. | |

Evidence is filled in above only where this phase actually measured
something (the two failure-mode Evidence cells); everywhere else is left
blank rather than guessed at. `docs/BENCHMARKS.md` still has no filled-in
Phase 1 numbers — the measurements taken here were correctness/behavioral
checks (memory bounded, lag rises and recovers, batch sizes observed), not
throughput/latency benchmarks, so they're recorded here rather than there.
