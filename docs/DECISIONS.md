# Decisions

## Phase 0

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| Use OTLP (`go.opentelemetry.io/proto/otlp`) as the wire format and span schema, rather than a hand-rolled schema | Custom protobuf/JSON span schema | OTLP is the de facto standard; every real instrumentation library (OTel SDKs, most vendor agents) already speaks it, so the collector works with real clients on day one instead of requiring a translation layer. Hand-rolling a schema means re-deriving decisions OTel already made (span kinds, status codes, resource attributes) with no benefit. | |
| Go for collector, writer, and loadgen, rather than Python | Python throughout, matching the analyzer | The collector and writer sit on the ingest hot path — high-throughput, concurrent, latency-sensitive. Go's concurrency model and static binaries (small containers, fast cold start, no interpreter/runtime overhead) fit that better than Python. Python is used for the analyzer instead, where the work is graph algorithms and statistics, not raw throughput. | |
| Redpanda (Kafka wire protocol) instead of Apache Kafka for local/dev | Kafka + Zookeeper (or KRaft) | Redpanda ships as a single binary/container with no separate coordination service, starts fast, and is Kafka-API-compatible so `franz-go` and any future Kafka-speaking client works unmodified. Lower local resource footprint and fewer moving parts for a docker-compose dev environment. Whether this choice holds for a production deployment is a later decision, not made here. | |
| ClickHouse `spans` table: `ORDER BY (trace_id, span_id)`, `PARTITION BY toDate(start_time)`, with a `service_name` set skip index | `ORDER BY (service_name, start_time)` | The table must serve two opposed access patterns: point lookup by `trace_id` (interactive, latency-sensitive) and p99 duration aggregation by `service_name` over a time range (tolerant of scanning). Leading the sort key with `trace_id` makes the interactive lookup fast via primary-key pruning; the aggregation query instead relies on partition pruning by date plus a set skip index on `service_name`, degrading to a columnar scan of two narrow columns rather than a full-table scan. Reasoning documented in full as a comment above the table in `deploy/clickhouse/init.sql`. If per-service aggregation becomes the dominant query pattern, the fix is an additional materialized view/projection ordered by `(service_name, start_time)`, not reordering this table's primary key. | |
| Three independent Go modules (`collector/go.mod`, `writer/go.mod`, `loadgen/go.mod`) tied together with a root `go.work` for local development | Single shared Go module for all three services | Each service ships as its own container with its own dependency footprint (e.g. `loadgen` doesn't need `clickhouse-go` or `franz-go`; `writer` doesn't need the gRPC server bits `collector` needs). Independent `go.mod` files keep each image's dependency graph minimal and let the services version independently later. `go.work` keeps cross-module local development (e.g. `go build ./...` from the repo root, IDE tooling) convenient without merging the modules. | |
| `collector` and `writer` container images: Alpine base instead of distroless | `gcr.io/distroless/static-debian12` | Both services need a docker-compose `healthcheck` that curls their own `/healthz` endpoint. Distroless images ship no shell and no HTTP client, so an in-container healthcheck isn't possible without adding a second binary. Alpine's bundled BusyBox `wget` covers this with negligible image-size cost over distroless, without pulling in a full OS. | |
| `collector` and `writer` expose `/healthz` and `/metrics` on a dedicated HTTP port, separate from `collector`'s gRPC port | Serve health/metrics on the same port/protocol as the main service traffic | OTLP traffic is gRPC; health checks and Prometheus scraping are plain HTTP. Splitting the ports avoids protocol-muxing complexity and matches the pattern most OTel-ecosystem components already use (e.g. OTel Collector's own `:13133` health and `:8888` metrics ports). | |
| `writer` stays running (serving `/healthz` and `/metrics`) after its Phase 0 startup connectivity checks pass, rather than checking connectivity and exiting | Exit 0 immediately after a successful connectivity check | docker-compose `healthcheck` and `depends_on: condition: service_healthy` require a long-running process to poll. An exit-on-success process would report as "exited (0)", which compose does not treat as healthy, breaking the deliberate dependency ordering (`prometheus` waiting on `writer`, etc.). | |
| `duration_ns` and `start_time` (DateTime64) as `MATERIALIZED` columns in the `spans` table, derived from the raw `start_time_unix_nano`/`end_time_unix_nano` fields | Store `duration_ns` as a value written directly by the writer | Deriving `duration_ns` from the two nanosecond timestamps guarantees it can never drift out of sync with them — there's only one source of truth. `start_time` as a materialized `DateTime64(9)` exists solely so `PARTITION BY`/TTL have a native date/time expression to operate on; the raw nanosecond epoch fields remain the fields the writer actually inserts. | |

Evidence is left blank throughout Phase 0 — nothing had been load-tested or
benchmarked yet at that point.

## Phase 1

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| Delivery semantics: at-least-once, deduplicated by ClickHouse `ReplacingMergeTree(ingested_at)` rather than by the writer | Exactly-once (transactional Kafka consume + ClickHouse insert), or dedup logic in the writer itself | Exactly-once across a consume-then-insert-into-a-different-system boundary requires distributed transactions or idempotency keys ClickHouse doesn't natively support well at this table's write volume. Pushing dedup to `ReplacingMergeTree` keeps the writer simple (insert, retry, commit — no dedup bookkeeping) and matches spans' natural idempotency: the same (trace_id, span_id) redelivered has identical content, so which copy "wins" a merge doesn't matter. Trade-off: readers must use `FINAL` (or accept eventual, merge-driven dedup) to see exact counts — not free, but confined to query time. | |
| Kafka partition key: raw `trace_id` bytes | Round-robin / no key (max throughput, no ordering guarantee); `span_id` (finer-grained, but scatters a trace's spans across partitions) | Every span of a trace must land on the same partition so a per-partition consumer sees them in a consistent relative order — load-bearing for Phase 2's topology reconstruction, which needs a trace's spans processed together. Kafka's default partitioner hashes the record key, so same key -> same partition is automatic; no custom partitioner needed. Verified with a unit test (`kafkaproducer.TestBuildRecordSameTraceIDSameKey`) that two spans sharing a trace_id always produce the same record key. | |
| Backpressure: an explicit bounded, blocking queue (`internal/boundedqueue`) between a dedicated fetch/decode goroutine and the batch/flush loop, rather than a single goroutine relying on franz-go's own fetch loop for backpressure | A single-goroutine loop — poll, decode, append to batch, flush on trigger, repeat — with no explicit queue and no second goroutine | Stated plainly: the simpler single-goroutine design would also have worked. franz-go's `PollFetches` naturally stalls fetching more records while the caller is busy (retrying a failed insert, in our case), so "stall, never buffer unboundedly" falls out of that loop for free, the same way it does here. The reason to add the queue and the second goroutine anyway was testability: it turns "the writer doesn't buffer unboundedly" from a claim about how we *use* a third-party client into a property of a small piece of code we own and can unit test in isolation (`boundedqueue.TestPushBlocksWhenFullAndUnblocksOnPop`) without spinning up Kafka. That benefit has a real cost, not just extra files: `flush` is now reachable from two goroutines (the batch loop and franz-go's `OnPartitionsRevoked` callback, which franz-go can invoke on its own goroutine at any time), so it's guarded by a mutex (`consumer.flushMu`) that wouldn't need to exist under the simpler design. That's a real piece of concurrent-correctness surface accepted purely so the backpressure property could be independently unit-tested — not because the extra machinery was required to make backpressure work. | Manual failure test: with ClickHouse stopped, writer memory stayed flat at 11.95MiB/7.749GiB (0.15%) over a sustained outage while consumer lag rose to ~2510 spans across 4 partitions — confirms growth went to Kafka lag, not process memory. |
| Batch flush: 5000 rows or 2 seconds, whichever fires first (both configurable via `WRITER_BATCH_MAX_SIZE` / `WRITER_FLUSH_INTERVAL`) | Fixed-size only (simpler, but stalls low-throughput partitions indefinitely); fixed-time only (simpler, but caps throughput at low-latency load) | Size-only starves the "trickle" case — a handful of spans/sec would sit unflushed forever below any reasonable size threshold. Time-only wastes batching efficiency under bursts big enough to hit a size bound well before the timer would. The OR-whichever-first policy is standard for this exact reason. | At the throughput levels exercised so far (up to ~150 spans/sec via loadgen), only the time bound has actually fired — `writer_batch_size` histogram shows all observed batches under 500 rows, well below the 5000 size trigger. The size-triggered flush path is unit-tested (`batcher.TestAddTriggersFlushAtMaxSize`) but not yet exercised by a real end-to-end run — see `docs/BENCHMARKS.md`'s "Known gap" note for the throughput math on why. |
| Kafka topic `spans`: 4 partitions, created explicitly by a one-shot `redpanda-topic-init` compose service before collector/writer start | Let the broker auto-create the topic on first produce (default partition count, usually 1) | Partition count is effectively fixed at creation time — changing it later reshuffles which keys land on which partition, breaking the "same trace_id always same partition" guarantee for any trace whose spans straddle the change. Deciding it explicitly, once, up front avoids that trap. 4 is enough to make partition-level behavior (skew, per-partition lag, rebalances) observable in Phase 6 without complicating local runs with a large partition count. | |
| Collector denormalizes `service.name` from the parent `Resource` onto each individual `Span`'s own attributes before publishing, rather than publishing OTLP's native `ResourceSpans` structure (Resource + spans) to Kafka | Publish a single-span `ResourceSpans` wrapper (one Resource, one ScopeSpans, one Span) per Kafka message, preserving full OTLP structure | I wanted one Kafka message per span, serialized as a literal OTLP `tracepb.Span` — not a wrapper message. But `service_name` (a dedicated, indexed column in the schema) lives on `Resource`, not `Span`. Copying it onto the span's own attributes before serializing keeps messages to a single flat `tracepb.Span`, staying protobuf end-to-end with no custom envelope, at the cost of ~20-30 bytes of duplicated attribute data per span. The writer strips it back out of the `Attributes` map column on the way in, since it already has its own column. | |
| Collector's `Export` RPC returns after admission to a bounded in-flight producer queue, not after the Kafka broker ack | Block `Export` until the broker acks every span in the request (synchronous, strongly consistent from the caller's point of view) | I wanted an async producer with a bounded in-flight limit, where a full buffer surfaces as a synchronous error back to the caller — that only makes sense if normal admission doesn't wait for the broker round trip either. The cost: `Export` can return success for a span that later fails to publish after retries are exhausted (broker down, etc.) — that span is silently lost from the caller's perspective, though not from ours: it's counted (`collector_publish_errors_total{reason="produce_failed"}`) and logged. I wanted that specific failure mode — a dropped span — to always be counted and logged rather than treated as a default best-effort outcome nobody has to think about. | |
| Integration tests (`/integration` module) drive the real `docker-compose.yml` stack via `docker compose` CLI calls (`os/exec`), rather than testcontainers-go | testcontainers-go, which manages containers programmatically from within the test process | I already had a working, hand-tuned `docker-compose.yml` with correct healthcheck-based dependency ordering; testcontainers-go would mean re-expressing that same topology a second way in Go code, or awkwardly wrapping `docker-compose.yml` through testcontainers' own compose support. Shelling out to the `docker compose` CLI directly reuses the compose file as the single source of truth and adds zero new dependencies to the module (stdlib only). Trade-off: requires a `docker` CLI with the compose plugin on `PATH` wherever these tests run — true in CI, and true for local dev, but not inside a bare `golang` container without also installing Docker's CLI into it. I confirmed this by cross-compiling the test binary in a `golang` container and running the resulting binary directly against the host's native Docker instead. | |
| Integration tests are gated behind a `-tags=integration` build constraint and are **not** part of the default `go vet`/`build`/`test`/`golangci-lint` CI matrix | Add `integration` as a fourth entry in the existing CI job's module matrix | They spin up the full docker-compose stack (build images, start 6 containers, run for ~1 minute) and stop/start a real container mid-test — appropriate for an on-demand or nightly job, not for every push/PR the way the fast unit-test matrix is. Excluding them from the default matrix keeps "CI green" meaning "the fast checks pass," not "a minute-plus Docker orchestration run passed." Wiring an actual CI job for them (with Docker available in the runner) is left for whenever that cost is worth paying, not built speculatively here. | |

## Phase 2 (partial: loadgen ground truth/fault injection + trace reassembly only)

Clock skew detection, service topology aggregation, and the accuracy-eval
harness are separate pieces of work I haven't built yet, so I'm not
recording decisions about them here as if they'd already been made — that
would be guessing ahead of doing the work.

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| Analyzer processes ClickHouse in epoch-aligned, fixed-size windows on a poll loop, not a streaming consumer | A real streaming pipeline (Kafka consumer group reading spans directly, à la the writer) | Windowed batch is simpler to reason about and test: a window's correctness doesn't depend on consumer group rebalances, partition assignment, or in-order delivery — it's "query a time range, process what's there." The cost is latency (a trace isn't reassembled until its window closes) and repeated ClickHouse scans instead of a continuous stream — both acceptable for what this phase needs to prove out first: whether reassembly is *correct*, not how fast it can go. | |
| Watermark delay of 30s (window size 60s) before a window is considered closed | A shorter watermark (less end-to-end lag) or a longer one (fewer late spans) | I don't have a measured spans-arrive-how-late-in-practice distribution yet, so I picked half the window size as a starting point that's easy to reason about, not a tuned value. This is the kind of number that should move once the fault sweep (unbuilt) shows how it trades off against late_spans_total. | |
| Windows are epoch-aligned (`floor(unix_seconds / window_seconds)`), anchored to the Unix epoch, not to analyzer startup time or a calendar day | Align windows to midnight, or to whenever the analyzer process starts | Epoch alignment means two analyzer instances (or a restarted one) agree on window boundaries without coordinating, and — the reason it's in this table — it's *why* the midnight-partition-straddle requirement turned out to be about the ClickHouse query, not the windowing logic: since 86400 is divisible by the default 60s window, midnight always lands exactly on a window boundary, so a window can never actually straddle it. What can straddle it is the SQL query if it's written as `toDate(start_time) = X` instead of a start_time range — see reader.py and its dedicated test in tests_integration/. | |
| Orphans (span whose parent_span_id doesn't resolve in the window) are recorded and classified, never dropped or reattached to a guessed parent | Silently drop spans with no resolvable parent; or attach them to the trace's root as a fallback | Both alternatives destroy information a later accuracy measurement needs: dropping loses the span entirely from any output, and reattaching to the root fabricates a parent/child relationship that was never real, which would corrupt exactly the "span attachment accuracy" metric this phase exists to eventually produce. Keeping every span, honestly labeled, is the only choice that doesn't quietly bias a future measurement. | |
| An orphan's own descendants are classified "ok" (reachable from the orphan), not swept into "cycle_rejected" just because they're unreachable from the trace's true root | Classify anything not reachable from a true root as one bucket (e.g. just "incomplete") | These are different failure signatures with different causes: a genuine cycle is malformed/impossible data, while a subtree hanging off an orphan is perfectly well-formed data that's simply missing *its own* ancestor. Conflating them would make "cycle_rejected" fire constantly in the completely ordinary case of a dropped mid-trace span with children — which is exactly what --drop-rate produces — making that classification useless for actually finding real cycles. The fix was seeding reachability from every orphan as well as every true root, and only labeling something cycle_rejected if it's unreachable from *both* sets. See reassembly.py's module docstring and `test_orphan_descendants_are_ok_not_cycle_rejected`. | |
| Ground truth is written by loadgen directly to ClickHouse (`ground_truth_spans`/`ground_truth_edges`), bypassing the collector/writer pipeline entirely | Send ground truth through the same collector -> Kafka -> writer path as real spans, tagged somehow to distinguish it | Ground truth has to record what was *generated*, before any fault runs — "faults must be applied after ground truth is recorded" is the one rule this whole phase hangs off. Routing it through the pipeline under test would make ground truth subject to the same drops/delays/reordering it's supposed to be the answer key for, which is circular. A direct write is also just simpler: loadgen already needs a ClickHouse connection for nothing else, so it's a small, explicit dependency rather than smuggling test-only semantics into the production ingest path. | |
| loadgen now requires ClickHouse connectivity at startup (fails fast if unreachable), same as writer | Make ground truth recording optional/best-effort, so loadgen still runs standalone against just a collector | Ground truth isn't a nice-to-have instrumentation add-on in this phase, it's the central mechanism the phase exists to build — a loadgen run with silently-skipped ground truth would produce traces with no way to ever check their accuracy. Fail-fast here matches the same reasoning collector and writer already use for their own required dependencies. | |
| Fault injectors operate on `[]spanplan.PlannedSpan` (span + service + Delay + Drop), and the emitter groups by actual Delay value before sending, rather than injectors mutating `[]*tracepb.Span` in place as the Phase 0 stub signature implied | Keep faults as pure span-content transforms (e.g. a "drop" fault just returns a shorter slice, as the original doc comment described) | Two of the fault types I wanted — out-of-order and late-arrival — are specifically about *when* a span is emitted, not what it contains. A `[]Span -> []Span` transform has nowhere to express "send this 90 seconds from now." Once delay had to be representable, drop became "a delay of never" naturally, so both live on the same PlannedSpan.Delay/.Drop pair rather than as different mechanisms. This meant changing loadgen's emit path from one Export call per trace to one call per (trace, delay-bucket) — more RPCs when a fault is active, none extra when it isn't (an all-zero-delay plan still sends as a single call). | |
| Clock-skew fault injection (`--clock-skew-rate`) was deferred until it could land in the same change as its detection, rather than shipping the injector alone first | Implement injection as soon as it's needed elsewhere, add detection in a later change | Shipping the injector without anything that can detect or account for it would mean a `--clock-skew-rate` flag sits in loadgen doing damage with no way to verify it's doing the *right* damage. Landing both together, once I got to this work, meant the very first time skew injection existed at all, there was already a measured detected-vs-true-offset number to check it against — see the row below, and the fault sweep in docs/BENCHMARKS.md. | |
| Analyzer reads ClickHouse over HTTP (`clickhouse-connect`, port 8123), not the native protocol the writer uses (`clickhouse-go`, port 9000) | Use a native-protocol Python client to match the writer's transport | No mature native-protocol client for Python matches clickhouse-connect's maturity/adoption; HTTP is simpler to reason about from Python (plain requests-style semantics, no wire protocol to get wrong) and perfectly adequate for windowed batch queries, which aren't latency-sensitive the way the writer's per-span inserts are. | |
| Analyzer's window and late-arrival queries use `SELECT ... FINAL` | Query without FINAL and accept that an unmerged ReplacingMergeTree duplicate (writer at-least-once redelivery) might appear as two rows | Reassembly logic assumes one row per real span; a still-unmerged duplicate would silently inflate span_count and could even fabricate a fake "multiple roots" or double-counted orphan. FINAL costs query-time merge work but guarantees the row count reassembly sees matches reality regardless of background merge timing. Revisit if this becomes a real bottleneck — nothing here has measured whether it is one. | |
| Late-span detection uses a single rolling cursor (`last_late_check` timestamp + the oldest still-open window's start as a boundary), not per-window precise bookkeeping | Track, per processed window, exactly when it was finalized, and check each window's own late-arrivals against its own finalization time | A single cursor is simpler and only trades precision at the margins: it can occasionally classify something as "late" a poll cycle earlier or later than the most precise per-window accounting would, but the count and the fact that it's not silently dropped — the actual requirement — hold either way. Reached for the more complex design only if the simple one turns out to be wrong, not preemptively. | |

## Phase 2 (deliverables 3-5: clock skew, service topology graph, accuracy eval)

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| A skewed service's clock offset is decided once (the first time that service is seen in a run) and held constant for the rest of the run; the root service is never skewed at all | Redraw a fresh random offset per span, or per trace; allow the root to be skewed too | A real clock doesn't drift second-to-second at fault-injection timescales — it's wrong by roughly a constant amount for as long as the process runs, so a per-run constant is the honest simulation. Keeping the root unskewed is what makes the whole scheme measurable at all: offsets are only ever recoverable *relative* to some reference (see clockskew.py's module docstring), and the root is that reference by construction (offset defined as exactly zero). Skewing it would mean its true offset is permanently invisible, folded as a constant bias into every other service's estimate instead of being its own reportable number. | |
| Per-service offset estimation anchors its baseline ("typical_gap") on whichever edge's typical gap has the smallest absolute value, not the median of all edges' typical gaps | Median of all edge medians (the first design, before live testing) | Found wrong by running it: a skewed *hub* service touches every edge connected to it, both incoming and outgoing. In the default topology, checkout is that hub — one skewed service there corrupts 4 of the graph's 5 edges, so a median-based baseline (needs a majority of edges clean) picks a skewed value as "typical" and the error propagates to every other service's estimate. True gaps are always small and positive; skew is configured with much larger magnitude. So "smallest absolute value" only needs *one* clean edge to work, a much weaker assumption — see docs/ISSUES.md for the actual bad numbers this produced before the fix, and the fix's own remaining limitation (still needs at least one clean edge to exist at all, which isn't guaranteed on a 5-edge topology at every fault rate or random draw — documented directly in clockskew.py rather than hidden). | See docs/BENCHMARKS.md's fault sweep for how offset error actually behaves across rates — reported honestly, including where it's bad. |
| Deliverable 4 (`service_edges`) and deliverable 3 (`service_clock_offsets`) both reuse a single shared helper, `reassembly.resolved_parent_child_pairs`, rather than each deriving parent/child linkage independently | Have topology_agg.py and clockskew.py each do their own trace-grouping and parent-lookup pass over the window's rows | Both need exactly the same thing — "which (parent, child) pairs actually resolve in this window" — and reassemble() already computes this internally as part of building each trace's tree. Extracting it once means a future third consumer of resolved pairs doesn't re-derive (and risk subtly re-deriving wrong) the same linkage logic a third time. | |
| `eval.py` is split into a ClickHouse-querying half (`evaluate`) and a pure-Python metrics half (`compute_metrics`) that takes plain sets/dicts and has no database dependency | One function that queries and computes together | The actual accuracy arithmetic (precision/recall, attachment accuracy, orphan accuracy, clock error) is the part worth being confident about — unit-testing it against hand-built ground truth/reconstruction data, with no ClickHouse involved, catches a wrong formula immediately rather than only when a live run happens to expose it. Splitting cost nothing structurally; `evaluate` is a thin set of `_fetch_*` calls feeding `compute_metrics`. | |
| Attachment accuracy and orphan accuracy are computed as `None` (reported as "N/A"), not `0.0` or `1.0`, when their denominator is zero | Report 0.0 (nothing measured "succeeded") or skip the field entirely | A run with no drop fault has zero true-orphan cases by construction — reporting `orphan_accuracy: 0.0` for that run would read as "the analyzer failed to classify any orphan correctly," when the true statement is "there was nothing to classify." `None`/"N/A" preserves the distinction between "measured and failed" and "nothing to measure," which matters a great deal once these numbers land in a table someone skims quickly. | |
| The fault sweep is driven by a bash script (`scripts/run_sweep.sh`) that shells out to a pre-compiled loadgen binary and the already-built analyzer Docker image, rather than a Python or Go orchestrator | Write the sweep driver in Python (reusing eval.py's language) or Go (reusing loadgen's) | The orchestration is entirely "run this container, wait, run that container, parse JSON" — no logic worth a real programming language's type system or test suite, and bash's job here is exactly what it's for. Compiling loadgen once up front and reusing the analyzer's already-built image (rather than `go run` and `pip install` on every one of 17 sweep points) turned out to matter: the first version's per-point overhead was large enough to be worth eliminating once measured. | |
| Sweep points use a shortened `--late-arrival-min/--late-arrival-max` (5s-15s) rather than loadgen's production-realistic default (2-5 minutes) | Run the sweep with production-scale late-arrival delay | A multi-minute delay multiplied across 4 late-arrival sweep points would dominate the sweep's total wall-clock cost for no corresponding gain in what's being measured — the analyzer's late-detection logic doesn't care whether the delay is 10 seconds or 10 minutes, only that it exceeds the watermark. This is a sweep-harness convenience, not a claim about realistic late-arrival timing; loadgen's own default flags (used by any real invocation without a `--late-arrival-min/max` override) are untouched. | |

## Phase 3 (deliverables 1-3: incident injection, baseline modeling, detectors)

Alert suppression and the accuracy-eval harness (deliverables 4-5) are
separate pieces of work I haven't built yet — not recorded here as if
they had been.

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| Incidents are a second, independent injection layer (`topology.IncidentSpec`, applied during `Generate`) — deliberately not folded into the existing `fault` package | Add incident types as more `fault.Injector` implementations alongside drop/out-of-order/late-arrival/clock-skew | The two layers answer different questions and operate on different data. `fault` injectors mutate a `[]spanplan.PlannedSpan` *after* generation — they corrupt how spans about a healthy system get delivered (dropped, reordered, delayed), and ground truth for them is recorded *before* they run, precisely so the fault is invisible to ground truth. An incident is the opposite: it changes what the simulated system actually *did* — a service really was slower, really did error — so it has to be applied *during* generation, and its ground truth (`ground_truth_incidents`) records what really happened, not what would have happened absent the fault. Conflating them would mean either faults start needing to touch span content (breaking the "faults never lie about what happened, they only affect delivery" invariant) or incidents would need to run post-generation and reconstruct timing/duration decisions the generator already made. Composing the same run with both a fault rate and an incident is a straightforward, meaningful thing to do (and Phase 3's eventual sweep may do it) — a mixed-purpose layer would make that harder to reason about, not easier. | |
| `latency_tail` inflates a fixed 5% of calls (not a configurable fraction) by `Magnitude`, while `latency_spike` multiplies the mean of every call | One combined "shift the whole distribution" mechanism, with the tail-vs-spike distinction expressed purely via `Magnitude` | The two incident types exist to be distinguishable by exactly the class of detector this phase builds: a mean/median-sensitive check should see `latency_spike` and miss `latency_tail`; a percentile-aware check should catch both. That only works if `latency_tail` structurally leaves the median alone — a *fraction*-based mechanism (5% of calls hit, 95% untouched) guarantees the median is untouched by construction, for any Magnitude. Making the 5% configurable would let a careless choice (e.g. 40%) blur the two incident types back together; fixing it keeps the distinction load-bearing rather than incidental. | Confirmed live: injecting `latency_tail` and checking the resulting window's `latency_p50_ms` showed no shift while `latency_p99_ms` did — see docs/ISSUES.md and the unit test `TestLatencyTailLeavesMedianUnaffectedButRaisesMax`. |
| Overlapping same-type incidents on one target compose multiplicatively for continuous multipliers (`latency_spike`, `latency_tail`, `throughput_drop`), but by maximum for `error_burst`'s probability | Multiply all of them together uniformly | `error_burst`'s Magnitude is itself already a probability in (0, 1]; multiplying two overlapping error-burst incidents together would silently *reduce* the effective error rate (0.6 * 0.6 = 0.36), the opposite of what stacking two incidents should mean. Taking the max keeps the result a well-formed probability that's at least as severe as either incident alone. The continuous multipliers don't have this problem — they're not bounded at 1, so multiplying them together is exactly "these two effects both apply." In practice this doesn't come up: every sweep point (and this phase's live verification) injects exactly one incident per run; the composition rule exists so a hand-authored topology YAML with genuinely overlapping incidents has defined, sane behavior rather than an accidental one. | |
| `edge_disappearance` always forces call probability to exactly 0 regardless of any simultaneously-active `throughput_drop` on the same edge, rather than composing the two | Multiply `throughput_drop`'s retained fraction into `edge_disappearance`'s (already-zero) effect, or let whichever incident type was added to `Config.Incidents` later win | A call can't be "partially nonexistent" — `edge_disappearance` firing at all means the edge is fully gone for that window, and no `throughput_drop` magnitude, however small, should be able to partially resurrect it. Checking `edge_disappearance` first and returning 0 immediately makes that true independent of insertion order, which matters because `Config.Incidents` order isn't otherwise a meaningful thing to reason about. | |
| Baseline latency/error statistics (median, MAD, error rate) are recomputed every window from the raw span-level lookback (up to 900s by default), not maintained incrementally or read back from previously-persisted baseline rows | Maintain a running/incremental estimate (e.g. an exponential moving average, or a streaming percentile sketch) updated window-to-window | Correctness first: an incremental estimate of a *median* is either wrong (EMA doesn't converge to the true median under a skewed distribution) or requires a real streaming-percentile data structure (t-digest or similar) that's a meaningfully bigger piece of engineering than this phase's scope justifies without evidence it's needed. Recomputing from raw data every window is provably correct and simple to test; its real cost is redundant I/O — up to `lookback_seconds / window_seconds` times more span data read than a truly incremental approach would need (at the default 900s/20s eval settings, roughly 45x). Accepted as a known, unoptimized tradeoff; a streaming estimator is the natural next step if this cost ever actually matters, not before. | Live-verified: a 120s run at rate=100 with the eval overlay's 20s windows processed every window in well under a second end to end (baseline refresh + detection + writes), so at this project's traffic scale the redundant-read cost hasn't been worth optimizing away. |
| A target's baseline lookback ends at the current window's *start*, strictly excluding the window being evaluated | Include the current window's own data in its own baseline (lookback ends at the window's end) | Excluding the current window is what makes "compare this window against history" a well-defined statement rather than "compare this window against history-plus-a-little-of-itself." It also makes the contamination behavior below cleanly describable: a baseline is built entirely from windows *before* the one being judged, so how fast an ongoing incident contaminates its own detection is purely a function of incident duration vs. lookback length, not conflated with within-window self-comparison. | |
| Baseline cold-start threshold (`ANALYZER_BASELINE_MIN_SAMPLES`, default 30) gates on individual call count in the lookback, not on number of windows observed | Require a minimum number of *windows* of history (e.g. 3) before considering a baseline ready | Call count is what the underlying statistics (median, MAD, error rate) actually need enough of to stop being noisy; window count is incidental. At this project's traffic scale (hundreds to thousands of calls per 20s window), 30 individual calls arrive within a fraction of a single window, so gating on windows instead would make the cold-start period *longer* than necessary for no statistical benefit. A very low-traffic target (rare edge, low call_probability) is exactly the case where "enough real observations" and "enough elapsed time" diverge, and call count is the one that actually reflects statistical confidence. | |
| Baseline contamination (an incident that runs long enough relative to the lookback becomes indistinguishable from "normal," silently ending detection) is handled by "use a long lookback relative to expected incident duration" plus documenting the failure mode — not by freezing the baseline while a detection is active | Freeze/exclude a window's data from future baseline computations once a detector has fired on it | Freezing needs detection state to decide what to exclude — but detection itself depends on the baseline that state would be excluded from. That's circular on the first pass: nothing has fired yet when the baseline that would eventually let something fire is being built. Breaking the circularity (e.g. a provisional/tentative freeze that gets revised) is real design work with its own failure modes (what if the tentative detection was itself a false positive? now clean data is wrongly excluded) that didn't seem justified without first knowing whether contamination is actually a practical problem at the incident durations this project's sweep will use. A long lookback is simple, has no failure mode of its own beyond "eventually still contaminates if the incident outlasts it," and that failure mode is exactly what gets measured and reported, not hidden. | Live-verified directly: injecting a 5x `latency_spike` on `checkout` immediately after only a 90s clean warm-up (short relative to the 900s default lookback) showed the baseline's median visibly drifting upward within 2-3 windows (~40-60s) as the incident's own data became a large fraction of the still-mostly-empty lookback — see docs/ISSUES.md. With a longer clean warm-up relative to the incident, the same mechanism produces much slower, more gradual drift, as intended. |
| `detect_call_rate_drop` falls back to a plain ratio check (`observed < median * 0.5`) when the baseline's call-rate MAD is exactly 0, instead of only using the robust z-score | Only ever use the robust z-score; report nothing when MAD is 0 | A MAD of 0 means every window in the lookback saw the *exact* same call count — a real, if unusual, possibility at fixed-rate synthetic load. The robust z-score has nothing to divide by in that case, but a call rate that's dropped to less than half of a nonzero, perfectly steady baseline is still obviously real signal, and `edge_disappearance` (observed calls == 0) is exactly the case this needs to not go silent on. The fallback only ever fires in this degenerate spread case — it never overrides or competes with the z-score when the baseline has any real variance. | |
| `detect_call_rate_drop` iterates over the *baseline* dict, not the current window's stats, and treats a target present in the baseline but absent from the current window as an observed call count of exactly 0 | Iterate over current window targets, and separately handle "absent from current" as its own case | This is what makes "the edge reported 0 calls" and "the edge reported nothing at all" the same well-defined thing rather than two cases needing separate logic: `current` is always built from *every* row process_window actually fetched for the window (see main.py), so a target's absence from it is never ambiguous — it reflects that the window genuinely produced zero matching spans/pairs, not that the window failed to process. Only targets that already have a baseline are ever considered at all, which is what distinguishes "this specific thing we track went silent" from "we have no idea what this is." | Live-verified: an `edge_disappearance` incident on `shipping->notifications` produced a clean `call_rate` detection with `observed_value=0` on exactly that edge, with sibling edges in the same window showing their real (nonzero, only mildly reduced) counts — not similarly zeroed out. |
| Percentile-deviation detection uses a **robust z-score** — `0.6745 * (x - median) / MAD`, equivalently `(x - median) / (1.4826 * MAD)` — not a plain z-score (`(x - mean) / stddev`) | Plain z-score against the baseline's mean/stddev | Latency is heavily right-skewed (a hard floor near zero, an unbounded tail of slow calls). A plain stddev is inflated by that tail, which cuts both ways badly: on a baseline that already has some slow-call tail, the inflated stddev can make a real, moderate spike look statistically unremarkable; on a very quiet baseline, ordinary variance can look anomalous by comparison to an artificially tight estimate. Median and MAD describe the typical case and the typical spread around it without being dragged around by the same tail the z-score is most sensitive to — the standard reason robust statistics exist for skewed data (Iglewicz & Hoaglin 1993). | |
| `detect_percentile_deviation` checks both the window's p95 and p99 against the baseline and fires on whichever deviates more, as one detector (not two separately-toggleable p95/p99 detectors) | Two independent detectors, one for p95 and one for p99 | p99 is what makes catching `latency_tail` possible at all (by construction, that incident type leaves p50 — and mostly p95 — untouched, only the top 1% moves). p95 remains useful as a slightly earlier/broader signal for `latency_spike`, which shifts the whole distribution. Keeping both under one detector name is simpler for the eventual per-detector-contribution analysis (deliverable 5) without losing anything: a target that fires only because of p99 and one that fires because of both are still both real, correctly-detected latency anomalies, and knowing exactly which percentile tripped it isn't needed to answer "did the percentile-deviation detector catch this incident type." | |
| `detect_error_rate_change` uses a pooled two-proportion z-test (current window's error rate vs. baseline's) with a minimum-sample-size guard, computed manually rather than via scipy | scipy.stats for the z-test / p-value | Comparing a z-statistic against a fixed threshold doesn't need an exact p-value from a normal CDF — the standard pooled-proportion z formula is a few lines of arithmetic, and adding a scipy dependency (a large, compiled package) for that would be disproportionate. Consistent with clockskew.py's existing choice to use stdlib `statistics` rather than pull in a stats library. | |
| Computed `Baseline` objects are written to ClickHouse (`service_baselines`/`edge_baselines`) every window purely for observability — the analyzer never reads them back to reconstruct state after a restart | Persist baseline state specifically so a restarted analyzer can resume from it without recomputing | "Baselines survive a restart" is satisfied by construction here, but not the way that phrase usually implies: nothing about the *computed Baseline objects* is durable state the process depends on — a restarted analyzer just recomputes every baseline fresh from spans/service_stats/service_edges, all of which were already durable in ClickHouse the whole time. The persisted `service_baselines`/`edge_baselines` rows exist so a person can query "what did the analyzer think was normal for checkout at time T," matching every other analyzer output being persisted (service_edges, service_clock_offsets) — not because anything reads them back. Worth being precise about this rather than letting "survives restarts" imply a stateful-recovery mechanism that isn't actually there. | |
| A single ad hoc incident can be injected via CLI flags (`--incident-type`/`--incident-target-*`/`--incident-magnitude`/`--incident-start`/`--incident-duration`), mirroring the Phase 2 fault flags, in addition to `Config.Incidents` being declaratively YAML-authorable (multiple, overlapping incidents) | CLI flags only (no declarative multi-incident config); or declarative config only (no CLI convenience) | The CLI path is what makes a single-incident-per-sweep-point harness (the shape Phase 2's sweep script already uses for fault types) trivial to drive without writing a topology YAML file per point. The declarative path is what the deliverable spec actually asks for ("incidents must be able to overlap in time") and is what a hand-authored scenario with several simultaneous incidents needs — CLI flags fundamentally can't express more than one incident. Both exist because they serve different callers: an automated sweep vs. a person constructing a specific scenario. | |
| **Known limitation, not fixed:** detection runs against a span's *total* duration (`end_time - start_time`), which for a non-leaf service already includes its children's cumulative time — not against *self time* (total duration minus the time spent inside direct children) | Compute self time in `service_agg.aggregate_services`/`topology_agg.aggregate_edges` and detect on that instead | Total duration is what's already on hand from the existing span-level fields with no further computation, and for a leaf service (no downstream calls) it's identical to self time anyway — so the gap was easy to miss until it was measured. It stopped being easy to miss once a `latency_spike` incident on `checkout` (a non-leaf service whose baseline duration is mostly its three children's cumulative time) produced only a ~2x observed shift from a 5x injected magnitude, while the identical magnitude on a leaf service (`inventory`) produced the full ~5x shift — see docs/ISSUES.md and docs/BENCHMARKS.md's depth breakdown for the actual measured numbers. The dilution isn't a detector bug; the detector is correctly measuring what it's given, and what it's given conflates "this service got slower" with "this service's downstream calls got slower," which are different facts a real on-call engineer would want told apart. **The remedy is understood but not implemented:** compute self time per span as `duration - sum(direct children's durations)` — using the same `resolved_parent_child_pairs` helper topology_agg and clockskew already share, one level of lookup rather than the fully recursive descendant sum, since only *direct* children double-count into a parent's total duration — and feed that into `service_agg`/`topology_agg`'s latency percentiles instead of raw span duration. Left undone here because it changes what every downstream consumer of those percentiles (including the already-built and already-measured baselines/detectors) means by "latency," and re-measuring the whole sweep against a redefined metric is a bigger change than this phase's remaining scope justifies without a deliberate decision to take it on. | See docs/BENCHMARKS.md's fault sweep, broken out by service depth, for exactly how much the dilution affects observed-vs-injected magnitude at each depth. |

## Phase 3 (deliverables 4-5: alert suppression, accuracy eval)

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| `group_detections` collapses a run of detections into one incident only on an *exact* back-to-back window run — a single missed window (a metric dipping just under threshold for one cycle) splits it into two separate incidents, with no gap tolerance | Allow a small gap (e.g. one missed window) without splitting the incident | A tolerance parameter is one more number to justify without evidence it's needed, and this project's incidents are short relative to a window (tens of seconds to a couple minutes against a 20s window), so a real incident producing more than an occasional single-window gap would itself be a finding worth seeing directly rather than smoothing over. If the sweep shows subtle-magnitude incidents flapping across the threshold and fragmenting into many tiny incidents, that's reported as-is (see docs/BENCHMARKS.md) rather than hidden by adding untested tolerance logic to make the numbers look cleaner. | |
| An incident's `incident_id` is a deterministic function of `(target, detector, start_window)`, not a random UUID | Random UUID per detected incident, tracked via in-memory or persisted mapping across analyzer restarts | Determinism is what makes `detected_incidents` a `ReplacingMergeTree` refresh-from-scratch table (like baselines) instead of stateful, incrementally-updated one: recomputing grouping over an overlapping lookback regenerates the *same* id for a still-ongoing incident, so a later insert with a wider `end_window`/updated peak is a natural update under the dedup key, not a duplicate needing reconciliation against previously-tracked state. A random id would need that state (what was this incident's id last time?) to exist somewhere and survive a restart — determinism sidesteps needing it at all. | |
| Propagation suppression only links two incidents when they share the *same detector* and their time windows *overlap* | Link any two concurrently-active incidents on topologically-adjacent services, regardless of detector | The propagation mechanism this project actually has is specific: a downstream service's *duration* inflates its ancestors' *duration* (see the self-time limitation entry above), which only explains latency-detector correlation, not, say, an ancestor's error rate rising because a descendant's latency did. Linking across detectors would attribute unrelated coincidences to each other with no underlying mechanism to justify it. | |
| Propagation suppression resolves each service-level incident to the *deepest* same-detector, time-overlapping incident reachable downstream — walking multiple hops, not just the immediate child — and edge-level incidents resolve through their callee to that same fully-resolved root, not to the callee's own (possibly still-derived) incident | Attribute each incident to its immediate downstream neighbor only (one hop), letting a chain of derived incidents point at each other in sequence | A single hop reproduces the propagation problem one level removed: on a `frontend -> checkout -> inventory` chain, one-hop attribution would mark `checkout` derived-from-`inventory` correctly, but `frontend` derived-from-`checkout` — technically not wrong, but not the answer an on-call engineer actually wants, which is "what's the real root," not "what's immediately upstream of me." This was caught by a failing unit test during development, not by design foresight: the first implementation of the edge-attribution half used the callee's own incident id directly instead of resolving through it, which passed every service-level test but failed the edge case (`frontend->checkout`'s root ended up pointing at `checkout`, two hops short of `inventory`) — see docs/ISSUES.md. | Live-verified on a real three-hop chain (`frontend -> checkout -> inventory`, all with a genuine `latency_spike` on `inventory`): both `checkout` and `frontend`'s incidents, and both `checkout->inventory` and `frontend->checkout`'s edge incidents, resolved directly to `inventory`'s incident — not to any intermediate hop. |
| `detected_incidents` is recomputed from a bounded trailing lookback of `detections` every window (`ANALYZER_GROUPING_LOOKBACK_SECONDS`, default 300s), the same correctness-over-incremental-state tradeoff as baselines — not incrementally extended in place | Track open incidents as in-process state, appending to them window-to-window and only touching ClickHouse to persist the final result | Same reasoning as `baseline.py`'s equivalent choice: recomputing from durable data is simple to get right and trivially correct after a restart, at the cost of repeatedly re-reading a bounded window of already-processed detections. The lookback (300s) only needs to comfortably exceed this project's actual incident durations (tens of seconds to a couple minutes in the sweep) — a real incident that somehow outlasted it would appear to end and restart at the lookback boundary, which isn't a concern at the durations actually in scope here. | |
| `eval.py`'s incident precision counts only **non-derived** analyzer incidents in its denominator — a correctly-suppressed propagated echo doesn't count as a false positive | Count every analyzer incident (derived or not) against precision, matching how edge precision counts every found edge | Found live, not designed upfront: a single real `latency_spike` on `inventory` (two hops deep) produced 16 total analyzer incidents — 1 real detection plus 15 correctly-identified derived echoes across ancestor services/edges — and counting all 16 against precision gave 0.0625 for what was, operationally, a perfect detection with perfect suppression. Precision is supposed to answer "of what the analyzer is presenting as an independent problem, how much is real" — a derived incident isn't being presented as independent, so it shouldn't be judged as if it were. This also makes precision a direct, honest measure of what suppression is worth: without it, precision would be dominated by exactly the propagation noise suppression exists to remove. See docs/ISSUES.md. | Re-verified after the fix on the same live scenario: precision moved from 0.0625 (1/16) to 0.25 (1/4) — the remaining 3 non-derived false positives are a real, separate, already-documented issue (run-boundary call_rate artifacts suppression has no topological explanation for, since they're simultaneous, not causally downstream of each other), not an artifact of this counting fix. |
| Incident precision and recall get **independent** None-vs-zero handling — a healthy-control run (no true incidents) with a false-positive detection reports `precision=0.0` (a real, meaningful zero) and `recall=None` ("nothing was true, so a fraction of true-things-found is undefined") — rather than the joint "both None only if both are empty" rule `compute_metrics` uses for edges | Reuse the exact same joint rule as edge precision/recall, for consistency across the file | Deliberately diverged from the existing, already-shipped edge-precision pattern rather than copying it verbatim, because this phase's healthy-control false-positive rate is the headline number the whole deliverable exists to produce (see the phase's own framing) — it deserves the more precise treatment even at the cost of the two metrics computing precision/recall slightly differently. Collapsing a healthy-control false positive into `recall=0.0` would misleadingly read as "a real incident was missed," when nothing was actually there to miss. Phase 2's edge metrics are unchanged; this isn't a retroactive correction of them, just a judgment that incident precision/recall warranted the extra precision where edge precision/recall didn't come up against a case where it mattered. | |
| Root-cause-accuracy's denominator only counts a derived incident if its own time window overlaps *some* true incident — a derived incident with no true incident anywhere near it (e.g. a run-boundary artifact suppression still tried to explain topologically) isn't counted at all, right or wrong | Count every derived incident against the denominator regardless of whether a true incident was anywhere nearby | A derived incident with no true incident to check against has no ground truth to be right or wrong *about* — counting it either way would either inflate the accuracy denominator with unanswerable cases or require inventing a default verdict for them. Restricting to incidents that overlap a true incident's window keeps the metric meaning exactly what it claims to mean: of the propagation calls suppression made about a *real* incident, how many pointed at the right place. | |
| Observed magnitude is computed with a **type-specific** formula chosen so its scale is directly comparable to the injected magnitude: `latency_spike`/`latency_tail` use peak p99 ÷ pre-incident baseline median; `error_burst` uses the observed error rate directly; `throughput_drop`/`edge_disappearance` use `1 - (observed call count ÷ baseline call rate)` | One generic "deviation" number (e.g. the detector's own z-score) for every incident type | A z-score isn't on the same scale as "5x" or "20% of calls" — reporting it next to the injected magnitude would invite a false comparison. Each type-specific formula was chosen to land on the same units and rough scale as what was actually injected, specifically so the depth-dilution effect (self-time limitation entry above) shows up as a direct, readable ratio in docs/BENCHMARKS.md rather than needing translation. | |
| `compute_depths` finds the topology's root structurally — whichever service never appears as a *callee* in the observed edge set — rather than taking a configured root service name as a parameter | Pass `cfg.root_service` (already used by clock-skew estimation) into the depth computation | `compute_depths` lives in eval.py, which evaluates a *run*, not a live analyzer process with a `Config` in scope — threading a root-service parameter through just for this would mean eval.py's CLI needing a new flag or environment variable duplicating information the topology itself already encodes unambiguously (this project's topology is always rooted, per topology/generate.go's own validation). Deriving it structurally keeps eval.py needing nothing beyond the run's own recorded data. | |
| The deliverable-5 sweep (`scripts/run_incident_sweep.sh`) runs one continuous loadgen process per point, with the incident scheduled mid-run via `--incident-start`/`--incident-duration`, rather than Phase 2's pattern of one short discrete process per sweep point | Reuse Phase 2's `run_sweep.sh` shape: a short (tens-of-seconds) process per point | Found live, before the sweep was even built: a finite loadgen process ramping from zero traffic at its own start and back to zero at its own end produces `call_rate` false positives on *every* service and edge in the windows straddling that boundary — real signal (call rate really did drop), but caused by the load generator stopping, not the simulated system failing. Phase 2's sweep never hit this because it didn't have a call-rate detector to trip. A sequence of many short processes back to back would produce a boundary artifact at every single transition, which would dominate — not just contaminate — this phase's healthy-control false-positive number, the one metric the phase explicitly asks to be reported honestly as the headline claim. One long run per point with a generous incident-free lead-in and tail keeps boundary-window contamination to (at most) the first and last of many windows, not a recurring event every few dozen seconds. | See docs/BENCHMARKS.md for how much of the remaining false-positive rate is still attributable to the run's own two boundary windows even under this design. |

## Phase 4 (deliverable 1: query API)

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| The query API is FastAPI, living inside the existing `analyzer` Python package (`analyzer/api/`), running as its own process/container (`uvicorn analyzer.api.app:app`) — same image as `analyzer`, different entrypoint | A standalone Go service, matching collector/writer's language; or embedding the API in the same process as `analyzer.main`'s poll loop | A Go service would need its own ClickHouse client, its own copy of every response shape this API returns, and would duplicate query logic this project already has working Python for (eval.py's `_fetch_*` functions are the direct ancestors of this API's `queries.py`) — for a read-only HTTP layer over data Python already reads correctly, that's pure duplication with no offsetting benefit. Embedding it in `analyzer.main`'s own process was rejected the other direction: that loop is a synchronous poll cycle (fetch a window, reassemble, detect, sleep), and an ASGI app serving concurrent browser requests has different concurrency needs and a different failure mode (a slow browser client shouldn't be able to stall window processing, and a stuck window shouldn't 502 a dashboard request). Separate processes sharing only the package's client/config code, not runtime state, keeps both simple. | |
| CORS is wide open (`allow_origins=["*"]`, `allow_methods=["GET"]`) | Restrict to the dashboard's own origin; add a proper auth layer | This API is unauthenticated, read-only, and sends no cookies or credentials — a permissive CORS policy doesn't expose anything an unauthenticated `curl` from anywhere else doesn't already have access to. Restricting the origin would only block the dashboard's own dev server (a different port, hence a different origin) without adding real protection, since anyone can already query the API directly. Revisit the moment auth is ever added — that's the point at which an open CORS policy stops being merely redundant and starts being a real hole. | |
| Every list endpoint enforces a server-side row cap (`API_MAX_ROWS`) and every endpoint requires an explicit time range no wider than `API_MAX_TIME_RANGE_SECONDS` — both enforced in `routes.py` before any query runs, not left to callers to self-limit | Trust callers to pass reasonable `limit`/range values; cap only in the SQL `LIMIT` clause | A `LIMIT` clause alone still lets a caller request an enormous, unbounded time range and pay (and make ClickHouse pay) the full scan cost before the limit ever trims the result — "no unbounded queries" has to be about query *cost*, not just response *size*. Enforcing both server-side, unconditionally, is also what makes this the one piece of genuinely new logic in this API worth unit testing (see `test_api_routes.py`) — everything else is a direct read of tables Phases 1-3 already populate correctly. | |
| `/api/topology` sums `call_count`/`error_count` across every window in the requested range, but reports latency percentiles from only the *most recent* window (`argMax(latency_p99_ms, window_start)`), not an aggregate across the range | Average each window's p50/p95/p99 into one range-wide percentile | **Percentiles aren't linear, so they can't be averaged the way counts can.** A percentile is an order statistic — it depends on the *rank* of a value within its own sample, not a quantity that adds or divides sensibly across samples. The mean of five windows' p99s is not the p99 of the union of those five windows' underlying calls; it's not even a reliable estimate of it, since the true combined p99 depends on how the *whole* distribution (not just each window's own tail) differs window to window. Two concrete ways the averaged number can be wrong: if traffic volume varies a lot between windows, a low-volume window's p99 (computed from very few samples, hence noisy) gets equal weight in the average as a high-volume window's p99, even though it represents far fewer actual calls, biasing the average away from what a true recombined p99 would show; and if the *underlying* per-call latency distribution genuinely shifted between windows (a real regression appearing partway through the range), averaging the two windows' p99s produces a number that was never true at any single moment, smoothing over exactly the kind of transition this project cares most about detecting. `argMax` avoids the whole problem by reporting one window's *real*, correctly-computed percentile rather than manufacturing a number with the right shape but no real meaning. The tradeoff is real and stated plainly: over a wide range, "latest window" can miss a spike that happened earlier in the range and has since subsided — a caller who needs that has to query `/api/detections` or a narrower `/api/topology` range instead. | |
| `GET /api/traces`' `min_duration_ms` filter is applied in Python, over a capped candidate set fetched from `trace_summaries` plus a bounded follow-up query against `tracing.spans` for just those candidates' durations — not in SQL over the full time/service-matched result — and the response says so via `duration_filter_truncated: bool` | Store trace duration on `trace_summaries` at reassembly time, so it's filterable in SQL directly; or apply the same compromise silently, documented only in code | `trace_summaries` doesn't store trace duration — it was never needed until this endpoint. Adding a column and populating it in `reassembly.py` was considered and rejected for this phase specifically: Phase 4's own constraint is "no new detection or reconstruction logic," and while trace duration is a trivial derivative of data reassembly already touches, changing what `reassembly.py` writes is still a change to Phase 2-3's output, not just a new read of it. The compromise itself (traces past `API_MAX_ROWS` candidates never get considered for duration filtering) was originally only documented in a docstring — a silent gap that contradicts this project's whole stance on surfacing uncertainty rather than hiding it (see the design thesis this phase opens with). `duration_filter_truncated` is set exactly when the candidate fetch came back at the cap while `min_duration_ms` was in play, so a caller — and the UI — knows the result may be incomplete rather than assuming it's exhaustive. Confirmed live to actually fire, not just in theory: a 5-minute window against this project's accumulated sweep traffic (~100 traces/sec) has tens of thousands of candidate traces against a 500-row cap. | |
| `GET /api/traces/{trace_id}` resolves clock-offset context (each trace service's most recent offset estimate at-or-before the trace's own start) server-side and includes it directly in the trace response, rather than leaving the frontend to query `/api/clock-offsets` separately and join | Have the frontend call `/api/clock-offsets` with a time range it computes itself, then join the results against the trace's own services client-side | A trace's own span timestamps span milliseconds; clock-offset estimates are per-analyzer-window, tens of seconds to minutes wide. A frontend join would need to correctly guess how wide a window to query around one trace's narrow timestamp, get it right for every trace it renders (a query range too narrow finds nothing; too wide risks picking up a stale or a too-early estimate), and pay a second round trip to do it. Resolving it server-side, once, using the same "most recent reading at or before a reference time" pattern already established in eval.py's baseline lookups, means the frontend's flame graph just reads `clock_offsets` off the trace response it already has. The real cost is a second, small query per trace-detail request (`service_clock_offsets` filtered to the trace's own handful of distinct services) — cheap, and worth paying once here rather than pushing the harder version of this problem onto every caller of this endpoint. Decided now, deliberately, because retrofitting it after the flame graph's rendering logic already assumed spans carry no clock context would have been the expensive order to do it in. | |
| List endpoints report `has_more: bool` (computed by fetching one row past the requested page) rather than a total match count | Run a separate `COUNT(*)` query alongside the paginated one | A `COUNT(*)` over the same filtered range roughly doubles every list request's query cost for a number most UIs don't actually need precisely — "is there more" (to show a Next button) is enough for exactly the paginated-table UI this API is built for. Precise total counts are a real thing to want for some UIs, just not for this one. | |

dividers, one muted monospace face for every number and timestamp (real

one plain sans for labels and navigation. Color is otherwise almost
absent; severity (`warning` = amber, `critical` = a controlled red,
`derived` = a deliberately dim gray, since a suppressed echo shouldn't
compete visually with an independent problem) is the only place it
appears at any intensity. Chosen specifically to avoid the two generic
directions named in the phase's own framing (near-black-plus-acid-accent,
cream-plus-serif-plus-terracotta) in favor of something closer to an
actual instrument panel — a register of *measurements*, not a marketing
surface, which is also this system's own self-description (see the
design thesis).

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| Both faces are system font stacks (`ui-monospace`/`Menlo`/`Consolas`/`monospace` for data, `-apple-system`/`Segoe UI`/`system-ui`/sans-serif for interface text), not a webfont | Load a specific typeface (e.g. JetBrains Mono, Inter) from Google Fonts or a bundled file | A webfont dependency buys marginal identity for a real cost (an external request this offline-capable local-dev tool doesn't otherwise have, or a bundled font file to maintain) — the system monospace stack already gives real tabular numerals (`font-variant-numeric: tabular-nums` plus the monospace metric itself) and a genuinely different visual register from the UI face, which is what the two-face requirement is actually for. Revisit if the console aesthetic ever needs to travel outside this project's own dev/demo context, where font availability can't be assumed the way it can on a developer's own machine. | |
| The service topology graph uses a deterministic, depth-layered layout (columns = BFS depth from the topology's structural root, rows within a column sorted alphabetically) computed fresh from the current edge set every render — not a force-directed physics simulation | Force-directed layout (e.g. d3-force), which produces more "organic" node spacing | A force simulation is iterative and its resting position depends on initial conditions and iteration count — the same graph re-laid-out on the next poll can settle into a visibly different arrangement even with identical data, which is exactly the "reshuffles on every refresh" failure the deliverable calls out as unreadable. A layered layout is a pure function of the edge set: the same topology always produces the same positions, and a topology that hasn't changed since the last poll produces a pixel-identical graph. The tradeoff is real — a layered layout can't represent a topology with genuine cycles as cleanly as a force layout might — but this project's topology is always a tree (loadgen's own generator guards against cycles), so the case a layered layout handles worse doesn't arise here. | |
| Large traces are handled by capping initial render to a fixed span count and depth, with per-subtree expansion — not virtualized scrolling (windowing) or canvas rendering | `react-window`/similar viewport virtualization; or render the whole flame graph to an HTML canvas instead of DOM nodes | Viewport virtualization for a flame graph is two-dimensional (both the visible time range *and* the visible depth range matter) and is a real, separate piece of engineering closer to a small layout engine than a dependency drop-in — out of proportion to this phase's scope discipline. Canvas rendering solves the DOM-node-count problem directly but trades away CSS styling and native hover/click semantics for manual hit-testing, which the "hovering a span shows detail" requirement needs. Capping and letting a person expand a dense subtree on demand is the simplest mechanism that actually bounds worst-case DOM node count, needs no new dependency, and is standard flame-graph UX (most production flame graphs collapse deep or repetitive subtrees by default). This project's own generated traces are small (single digits to low tens of spans) — the cap was written to be correct and was verified with a synthetic large trace in a component test, not against real data, since nothing in this project's own topology produces one. | |

## Phase 6 (harness: resource limits, failure definition, generator ceiling)

| Decision | Alternative considered | Rationale | Evidence |
|---|---|---|---|
| Docker resource limits (`deploy/docker-compose.load.yml`) sized against Docker Desktop's actual allocation (15 CPU / 7.75GiB, confirmed via `docker info`), not the host's full spec (Apple M5 Pro, 15 cores, 24GiB) | Size against the host machine's own totals | The Docker Desktop VM's allocation is the real ceiling every container actually competes inside — the host having more RAM than Docker was given is irrelevant to what a container can do. Getting this wrong (sizing against 24GiB) would produce limits that sum to more than what's actually available, defeating the entire point of pinning them. | |
| CPU limits sum to ~10.75 of the available 15 cores, deliberately leaving ~4.25 unclaimed rather than allocating close to the ceiling | Allocate the full 15 cores across services, on the assumption the load generator runs as separate, unlimited containers anyway | The load generator isn't outside this resource budget just because it isn't a compose service — it's still competing for the same Docker Desktop VM's cores. Calibration found a single loadgen process can't sustain this phase's higher steps alone (see the generator-ceiling row below), so the harness runs several loadgen containers in parallel; if the pipeline's own limits claimed everything, the generator would be starved by the very stack it's supposed to be loading, and every result downstream would be ambiguous between "the pipeline was slow" and "the generator couldn't offer the rate it claims to have offered." Reserved headroom for the generator is table stakes for a benchmark whose results need to mean what they say. | |
| Memory limits sum to 7.0 of 7.75GiB (leaving ~10% headroom for the Docker Desktop VM's own overhead), while CPU limits are treated as soft/throttling | Size memory the same way as CPU, close to the ceiling | Memory limits in Docker are hard: a container that exceeds `mem_limit` gets OOM-killed outright, not throttled the way CPU is. A benchmark that occasionally kills a service just from configured headroom being too tight — independent of whether the *pipeline itself* is actually failing — would misattribute a harness artifact as a finding. CPU can be allocated tighter to the ceiling because oversubscription there degrades gracefully (contention, not termination). | |
| ClickHouse's built-in Prometheus exporter (shipped commented-out in the stock image's `config.xml`) is enabled via a `config.d` override (`deploy/clickhouse/prometheus-metrics.xml`), mounted only by the load compose overlay | Add a separate `clickhouse-exporter` sidecar container | ClickHouse already ships this capability; turning it on costs one small XML file and a port, not a new container with its own resource footprint and failure mode to reason about. Scoped to the load overlay specifically (not the base compose file) because the default profile has never needed ClickHouse-side Prometheus metrics and doesn't gain anything from carrying the extra scrape target. | |
| Prometheus's scrape interval is tightened to 5s for load testing (`deploy/prometheus/prometheus-load.yml`), separate from the default profile's 15s | Keep the default 15s interval for load testing too | A ramp step can be held for as little as 2 minutes — at 15s that's 8 samples, not enough resolution to tell *when* within a step a metric started moving, and short-lived spikes between scrapes are invisible entirely. This is also what makes "capture the moment of failure" (deliverable 7) achievable at all — a lag graph needs enough points to show a slope, not just two dots. Not applied to the default profile: more samples stored for the same retention window is a real cost not worth paying for that profile's much lower-frequency needs. | |
| Failure is defined, for the ramp's automatic stop condition, as summed `writer_consumer_lag` across all 4 partitions being higher at the end of a held step than at the end of the previous step — i.e. lag still *growing* when the hold ends, not merely nonzero | A multi-condition OR (lag growth, nonzero span loss, end-to-end latency over some bound, a component OOM/restart) | Span loss, latency blowup, and OOM are downstream *consequences* of the pipeline no longer keeping pace, not independent earlier signals of it — by the time any of those show up, sustained lag growth has usually already been present for a while. A single, precisely-measurable trigger (already-collected consumer lag, needing no new instrumentation or arbitrary latency threshold) is easier to reason about and impossible to leave ambiguous about which condition actually fired. The other three are still recorded at every step as supporting evidence — see docs/BENCHMARKS.md — just not wired to the ramp's stop condition. | |
| The load harness converts every spans/sec target to loadgen's `--rate` flag (traces/sec) using this topology's fixed expected spans/trace (5.5575, derived from each edge's call probability), and fans out into multiple parallel loadgen processes once the per-process rate would exceed ~600 traces/sec | Trust `--rate` as spans/sec directly (it isn't — the flag is documented as traces/sec but easy to misread as this phase's own spans/sec framing); run a single process at whatever rate is requested | Calibration (15s bursts against the live collector) found a single loadgen process's ticker-driven generation loop stays >98% efficient (measured `traces_generated` close to `rate * duration`) up to ~700 traces/sec, then degrades — 89% at 900, and inconsistently 55-82% at 1000+ across repeated identical trials, with real collector-side `kafka publish buffer full` errors appearing at the higher end. Trusting the requested `--rate` as the true offered load above this point would silently understate it and misattribute the load generator's own ceiling to the pipeline being tested. See docs/ISSUES.md for the calibration data. 600 traces/sec/process leaves comfortable margin below where degradation was still negligible (700). | |
